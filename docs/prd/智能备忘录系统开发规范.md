# 智能备忘录系统开发规范

## 1. 文档目标

本文档定义智能备忘录系统的研发协作规范，包括代码结构、分支管理、接口规范、数据库规范、前端规范、后端规范、AI/ASR 规范、蓝牙规范、推送规范、测试规范、发布规范和安全规范。

适用范围：

- Flutter 移动端和平板端。
- React Web 端。
- Electron PC 端。
- Spring Boot 后端服务。
- Python FastAPI AI / ASR 服务。
- 数据库、缓存、消息队列、搜索、对象存储。

## 3. 分支与提交规范

### 3.1 分支

| 分支 | 用途 |
| --- | --- |
| main | 生产稳定版本 |
| develop | 开发集成分支 |
| feature/* | 新功能开发 |
| fix/* | 缺陷修复 |
| release/* | 发布准备 |
| hotfix/* | 生产紧急修复 |

示例：

```text
feature/memo-crud
feature/asr-task
fix/sync-conflict
release/v1.0.0
hotfix/push-token-expired
```

### 3.2 提交信息

使用 Conventional Commits。

```text
feat(memo): add memo archive API
fix(sync): resolve deleted memo conflict
test(ai): add summary schema validation tests
docs(arch): update bluetooth protocol
```

类型说明：

| 类型 | 说明 |
| --- | --- |
| feat | 新功能 |
| fix | 缺陷修复 |
| refactor | 重构 |
| test | 测试 |
| docs | 文档 |
| chore | 工程配置 |
| perf | 性能优化 |
| ci | CI/CD |

## 4. 通用代码规范

- 所有代码必须通过格式化工具。
- 所有服务必须支持健康检查接口。
- 所有外部调用必须设置超时。
- 所有异步任务必须具备幂等能力。
- 所有数据库写入接口必须记录操作人和更新时间。
- 所有删除操作默认使用软删除，物理删除必须经过评审。
- 所有敏感配置不得写入代码仓库。
- 所有新增功能必须补充最小必要测试。

## 5. 前端开发规范

### 5.1 Flutter 规范

目录建议：

```text
lib/
  core/
    config/
    network/
    auth/
    storage/
    logging/
  features/
    memo/
    voice/
    ai/
    sync/
    bluetooth/
    notification/
  shared/
    widgets/
    models/
    utils/
```

要求：

- 页面按 feature 组织，不按技术类型堆叠。
- 网络请求统一走 API Client。
- 本地缓存统一封装，禁止页面直接操作底层存储。
- 蓝牙、录音、推送等平台能力必须封装为 service。
- 所有用户可见错误必须有明确提示。
- 同步中、转写中、AI 处理中必须有状态展示。
- 离线状态下允许编辑，恢复网络后进入同步队列。

### 5.2 React Web 规范

目录建议：

```text
src/
  app/
  features/
    memo/
    search/
    ai/
    sync/
    settings/
  shared/
    api/
    components/
    hooks/
    stores/
    utils/
```

要求：

- 使用 TypeScript 严格模式。
- API 类型由 OpenAPI 或共享类型生成。
- 状态管理按业务复杂度选择 Zustand / Redux Toolkit / React Query。
- 所有表单必须有校验。
- WebSocket 连接必须支持重连和心跳。
- 禁止在组件中硬编码接口地址、模型名称、推送 key。

### 5.3 Electron 规范

要求：

- 主进程只处理系统能力和窗口生命周期。
- 渲染进程不得直接访问 Node.js 敏感 API。
- IPC 通信必须定义白名单。
- 本地文件读写必须校验路径和权限。
- 桌面通知必须遵循用户通知开关。
- 蓝牙能力优先封装在独立模块中，避免散落在 UI 组件里。

## 6. 后端开发规范

### 6.1 Spring Boot 服务结构

```text
src/main/java/com/company/smartmemo/memo/
  api/
  application/
  domain/
  infrastructure/
  config/
```

| 层 | 职责 |
| --- | --- |
| api | Controller、DTO、接口入参校验 |
| application | 应用服务、事务编排、用例逻辑 |
| domain | 实体、值对象、领域规则 |
| infrastructure | Repository、外部服务、MQ、缓存 |
| config | 配置类、安全、OpenAPI、Bean |

要求：

- Controller 不写业务逻辑。
- Service 方法必须表达业务意图。
- Repository 只负责数据访问。
- 跨服务调用必须通过 adapter 封装。
- 事务边界放在 application 层。
- 异常统一转换为标准错误响应。

### 6.2 Python AI / ASR 服务结构

```text
app/
  api/
  core/
  providers/
    deepseek/
    funasr/
    aliyun_asr/
  tasks/
  schemas/
  services/
  tests/
```

要求：

- 所有模型调用通过 provider adapter。
- prompt 必须版本化。
- 模型输出必须做 JSON schema 校验。
- 失败必须记录供应商、模型、耗时、错误码。
- 长任务必须异步执行，不能阻塞 HTTP 请求。
- 不允许在代码中硬编码 API Key、模型 ID、供应商地址。

## 7. API 设计规范

### 7.1 URL 命名

使用 REST 风格，统一加版本前缀。

```text
GET    /api/v1/memos
POST   /api/v1/memos
GET    /api/v1/memos/{memoId}
PATCH  /api/v1/memos/{memoId}
DELETE /api/v1/memos/{memoId}
POST   /api/v1/asr/tasks
GET    /api/v1/asr/tasks/{taskId}
POST   /api/v1/ai/summary
POST   /api/v1/sync/pull
POST   /api/v1/sync/push
```

### 7.2 响应格式

```json
{
  "code": "OK",
  "message": "success",
  "data": {},
  "traceId": "018f4f79-7c6f-7d61-8fd9-8b63d6c5c20a"
}
```

错误响应：

```json
{
  "code": "MEMO_NOT_FOUND",
  "message": "备忘录不存在",
  "data": null,
  "traceId": "018f4f79-7c6f-7d61-8fd9-8b63d6c5c20a"
}
```

### 7.3 分页格式

```json
{
  "items": [],
  "nextCursor": "cursor-value",
  "hasMore": true
}
```

### 7.4 错误码规范

| 前缀 | 模块 |
| --- | --- |
| AUTH_* | 认证鉴权 |
| USER_* | 用户 |
| MEMO_* | 备忘录 |
| SYNC_* | 同步 |
| ASR_* | 语音识别 |

| SYS_* | 系统 |

## 8. 数据库规范

### 8.1 命名

- 表名使用小写 snake_case，复数形式：`memos`、`memo_tags`。
- 字段名使用小写 snake_case：`created_at`、`updated_at`。
- 主键统一使用 `id`。
- 外键字段使用 `{entity}_id`：`user_id`、`memo_id`。
- 布尔字段使用 `is_`、`has_` 前缀。

### 8.2 通用字段

所有核心业务表建议包含：

```sql
id
created_at
updated_at
created_by
updated_by
deleted_at
version
```

### 8.3 索引规范

- 查询条件字段必须建立索引。
- 联合索引按区分度和查询顺序设计。
- 大文本字段不直接建立普通索引，全文搜索进入 Elasticsearch / OpenSearch。
- 同步相关表必须包含 `user_id`、`updated_at`、`version` 索引。

### 8.4 迁移规范

- 数据库结构变更必须使用 Flyway / Liquibase。
- 禁止直接在生产数据库手动改表。
- 生产变更必须提供回滚方案。
- 大表字段变更必须评估锁表风险。

## 9. 消息队列规范

### 9.1 Topic 命名

```text
memo.changed
sync.changed
asr.request
asr.completed
ai.request
ai.completed
push.request
search.index
```

### 9.2 消息格式

```json
{
  "eventId": "018f4f79-7c6f-7d61-8fd9-8b63d6c5c20a",
  "eventType": "memo.changed",
  "occurredAt": "2026-06-04T10:00:00+08:00",
  "userId": "user-id",
  "aggregateId": "memo-id",
  "payload": {},
  "traceId": "trace-id"
}
```

要求：

- 消息必须带 `eventId`，消费者根据 `eventId` 幂等处理。
- 消息必须带 `traceId`，便于链路追踪。
- 消费失败必须进入重试或死信队列。
- 事件 schema 变更必须兼容旧消费者。

## 10. AI 与 ASR 开发规范

### 10.1 模型调用

- 所有模型调用必须经过 `model-gateway` 或 provider adapter。
- 模型名称、temperature、max_tokens、timeout 必须配置化。
- 摘要、分类、标签等任务温度建议 0.2 至 0.5。
- 创意类内容才允许使用更高温度。
- 模型输出必须做 JSON schema 校验。
- 失败时按供应商、模型、任务类型记录日志和指标。

### 10.2 Prompt 规范

prompt 文件命名：

```text
summary.v1.md
tagging.v1.md
todo_extract.v1.md
conflict_merge.v1.md
```

要求：

- prompt 必须有版本号。
- prompt 修改必须走代码评审。
- prompt 中必须明确输出 JSON 格式。
- prompt 不得包含真实用户隐私样例。

### 10.3 ASR 规范

- 音频上传后先生成 ASR 任务，不同步阻塞等待长音频结果。
- ASR 结果必须保留原始文本和清洗后文本。
- ASR 失败必须支持重试。
- ASR 供应商调用必须记录耗时、失败原因和音频时长。
- 服务端统一处理音频格式转换。

## 11. 蓝牙开发规范

- 蓝牙设备必须先绑定用户后才能上传数据。
- BLE Service UUID 和 Characteristic UUID 必须在文档中登记。
- 数据帧必须包含协议版本、seq、type、payloadLength、crc。
- 客户端必须处理 MTU 不足导致的分包。
- 客户端必须支持断线重连和重复数据去重。
- 设备状态必须同步到服务端。
- 蓝牙调试日志不得包含敏感 payload 明文。

## 12. 推送开发规范

- 推送服务统一接收业务推送事件。
- 业务服务不得直接调用 APNs、FCM 或厂商推送。
- 推送 token 绑定到用户设备，不绑定到用户账号本身。
- token 失效后必须更新设备状态。
- 推送内容不得包含敏感备忘录正文。
- 在线设备优先走 WebSocket，离线设备走系统推送。
- 每条推送必须记录发送状态和失败原因。

## 13. 安全规范

- 所有接口必须走 HTTPS / WSS。
- 认证使用 JWT Access Token + Refresh Token。
- Refresh Token 必须支持吊销。
- 密码必须使用强哈希算法存储。
- 文件下载必须校验用户权限。
- 录音、图片、附件不得公开访问。
- API Key、数据库密码、推送证书必须通过 Secret 管理。
- 日志不得记录完整 Token、密码、API Key、手机号、邮箱、备忘录正文。
- 用户删除账号时必须支持数据清理或匿名化。

## 14. 测试规范

### 14.1 测试类型

| 类型 | 范围 |
| --- | --- |
| 单元测试 | 工具函数、领域规则、数据解析、冲突合并 |
| 接口测试 | REST API、鉴权、错误码、分页 |
| 集成测试 | 数据库、Redis、Kafka、ES、对象存储 |
| E2E 测试 | 登录、创建备忘录、语音转写、AI 摘要、多端同步 |
| 兼容性测试 | iOS、Android、Web、PC、蓝牙硬件 |
| 性能测试 | API QPS、ASR 并发、AI 任务吞吐、同步延迟 |
| 安全测试 | 权限越权、Token 过期、文件访问、注入攻击 |

### 14.2 最低要求

- 后端核心服务必须有单元测试和接口测试。
- 同步服务必须覆盖冲突场景。
- AI 服务必须覆盖 schema 校验和失败降级。
- 蓝牙模块必须覆盖断线重连、重复数据、分包组包。
- 推送服务必须覆盖 token 失效、重复推送、失败重试。

## 15. CI/CD 规范

流水线阶段：

```text
lint -> test -> build -> security scan -> image build -> deploy dev -> integration test -> deploy test/staging
```

要求：

- 所有 PR 必须通过 lint 和测试。
- 主分支禁止直接提交。
- 镜像必须使用不可变版本号。
- 发布前必须生成变更记录。
- 生产发布必须支持回滚。
- 数据库迁移必须在发布前单独验证。

## 16. 日志与监控规范

### 16.1 日志字段

```json
{
  "traceId": "trace-id",
  "userId": "user-id",
  "service": "memo-service",
  "level": "INFO",
  "message": "memo created",
  "timestamp": "2026-06-04T10:00:00+08:00"
}
```

要求：

- 所有请求必须生成 traceId。
- 异步消息必须传递 traceId。
- 日志不得包含敏感数据。
- 错误日志必须包含错误码和关键上下文。

### 16.2 监控指标

- API P95 / P99 延迟。
- API 错误率。
- 数据库慢查询。
- Redis 命中率。
- Kafka 消费堆积。
- ASR 成功率和平均耗时。
- AI token 消耗和调用成本。
- 推送成功率。
- 同步冲突数量。
- 蓝牙连接成功率。

## 17. 发布规范

发布步骤：

1. 合并 release 分支。
2. 生成版本号和变更记录。
3. 执行自动化测试。
4. 执行数据库迁移预检查。
5. 部署到 Staging。
6. 执行冒烟测试。
7. 灰度发布生产。
8. 观察监控指标。
9. 全量发布。

回滚要求：

- 服务镜像支持回滚到上一稳定版本。
- 数据库迁移必须评估是否可回滚。
- 推送、AI、ASR 等外部供应商配置支持快速切换。

## 18. PR 评审清单

提交 PR 前必须确认：

- 代码通过格式化和 lint。
- 新增功能有测试或说明未测试原因。
- 接口文档已更新。
- 数据库变更有迁移脚本。
- 新增配置有默认值和说明。
- 未提交密钥、证书、Token。
- 日志不包含敏感信息。
- 异步任务具备幂等处理。
- 外部调用设置了超时和重试。
- 重要变更有回滚方案。

## 19. MVP 开发执行顺序

1. 搭建基础仓库、Docker Compose 和 CI。
2. 完成 API Gateway、用户服务、鉴权。
3. 完成备忘录 CRUD、标签、分类、附件。
4. 完成 Flutter / Web 基础页面。
5. 完成 ASR 任务创建、录音上传、转写回填。
6. 完成 AI 摘要、标签推荐、待办提取。
7. 完成基础增量同步和 WebSocket 通知。
8. 完成推送服务基础能力。
9. 完成蓝牙设备绑定和数据上报 MVP。
10. 完成测试、灰度、上线和监控。
